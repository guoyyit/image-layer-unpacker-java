# image-layer-unpacker-java

容器镜像分层解包与合并视图文件系统服务。镜像由多个只读层（tar 归档）组成，
服务逐层解包、按顺序叠加为单一合并视图，并通过 HTTP 接口提供层解包、
合并视图读取与层管理能力。全部数据落在本地目录，不依赖任何外部服务。

## 构建与运行

```bash
mvn package                 # 构建并运行全部测试
mvn spring-boot:run         # 启动服务，默认端口 8080
```

配置项（`application.properties`，前缀 `unpacker.`）：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `unpacker.root-dir` | `./data` | 存储根目录（暂存 tar、层 rootfs、元数据） |
| `unpacker.max-layer-bytes` | 256MB | 单层解压后最大字节数 |
| `unpacker.max-total-bytes` | 2GB | 所有已提交层总占用上限 |
| `unpacker.max-entries-per-layer` | 100000 | 单归档最大条目数 |

## HTTP API

| 方法与路径 | 说明 |
| --- | --- |
| `POST /api/layers/{id}` | 上传并解包一层（body 为 tar 字节流，`application/octet-stream`）。幂等：已提交的同名 id 直接返回现有元数据 |
| `GET /api/layers` | 按叠加顺序列出全部层及状态（`UNPACKING`/`COMMITTED`/`FAILED`） |
| `DELETE /api/layers/{id}` | 删除层并回收空间；有读者持有时等待其结束后回收 |
| `GET /api/view/tree?path=/dir` | 列出合并视图中某目录的内容 |
| `GET /api/view/file?path=/f` | 下载合并视图中的文件内容 |

错误响应统一为 JSON：`{"error": "...", "message": "..."}`。恶意/损坏归档返回
`400 UNPACK_FAILED`，路径不存在返回 `404`，并发冲突（如同 id 正在解包）返回 `409`。

## 合并语义

层按提交顺序自下而上叠加，读取合并视图时遵循 overlayfs 风格语义：

- **文件覆盖**：上层同名文件遮蔽下层同名文件。
- **目录合并**：同名目录的内容跨层合并；逐名字解析，上层优先。
- **类型替换**：上层可以把下层的文件替换为目录（或反之）。
- **删除标记（whiteout）**：层内名为 `.wh.<name>` 的文件表示删除下层同目录下的
  `<name>`（文件或整个目录树）。标记本身永不暴露在合并视图中。
- **不透明目录**：层内目录 `<dir>/.wh..wh..opq` 表示 `<dir>` 为不透明目录，
  下层该目录的全部内容被隐藏，只保留上层内容。标记同样不暴露。
- 同一层内，若删除标记之后出现同名真实条目，真实条目生效（后者覆盖前者）。

## 安全边界

解包器在提取 tar 时强制执行以下策略，任一违规即整层拒绝：

- **路径穿越**：拒绝绝对路径、任何 `..` 路径段、NUL 字符；提取目标始终限制在
  层 rootfs 内。
- **链接逃逸**：符号链接目标必须是相对路径且（相对链接所在目录解析后）不越出
  层根；硬链接目标必须已存在于本层之内。读取文件时再次校验真实路径未越出层根
  （纵深防御）。
- **特殊文件**：拒绝字符/块设备、FIFO 等一切非常规文件/目录/链接的条目。
- **损坏归档**：tar 大小必须是 512 的整数倍且以两个零块结尾，否则视为截断；
  提取过程中的任何 IO/格式错误都使整层失败。
- **配额**：单层解压大小、单层条目数、已提交层总占用均有上限。超限即拒绝，
  且不留下任何痕迹（服务保持原状）。

失败的解包不会留下部分状态：提取在独立暂存目录进行，失败即整体清理；
暂存 tar 在提交成功后立即删除。

## 并发模型

- 解包只操作私有暂存路径，提交时才在监视器锁内一次性翻转状态，因此读者
  永远不会看到写了一半的层。
- `openView()` 在锁内固定（pin）当前已提交层集合，视图即一份自洽快照；
  之后提交的新层不影响该视图，也不会出现跨层混合状态。
- 删除先将层从叠加序列摘除（新读者无法附着），再等待已固定的读者结束，
  最后回收磁盘空间。删除与解包并发时按锁序串行，行为确定。
- 同一 id 并发解包：一个获胜，其余收到 `409` 或在提交后幂等返回。

## 持久化与崩溃恢复

```
<root>/staging/<id>.tar      上传暂存（恢复来源），提交成功后删除
<root>/layers/<id>/rootfs/   该层解压内容
<root>/layers/<id>/meta.json 元数据与解包日志（状态机）
```

重启时按 `meta.json` 恢复：

- `COMMITTED`：直接接管，**绝不重复解包**。
- `UNPACKING`：崩溃中断的层。暂存 tar 仍在则清除半成品 rootfs 后重新解包；
  tar 缺失则标记 `FAILED`。
- `FAILED`：保持失败态，可通过重新上传同 id 重试（先清理后解包，结果确定）。
- 无元数据的孤儿目录/暂存 tar 一律清理。

## 测试

`src/test/java/.../tests/` 下 45 个用例覆盖：

- `MergeSemanticsTest`：覆盖、目录合并、whiteout 删除、不透明目录、类型替换
- `ArchiveSecurityTest`：路径穿越、绝对路径、链接逃逸、设备文件、截断/损坏
  归档、配额拒绝、失败重试确定性、幂等重传
- `ConcurrencyTest`：解包期间并发读取的一致性、删除等待读者、同 id 并发解包
- `RecoveryTest`：崩溃后已完成层不重复解包、中断层重解包、孤儿清理、失败态持久
- `QuotaAndDeleteTest`：总配额拒绝且保持现状、删除回收配额与文件、中间层删除
- `HttpApiTest`：HTTP 端到端生命周期与错误响应
